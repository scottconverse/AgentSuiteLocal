# AgentSuiteLocal v1.0 Milestone Plan

**Status:** Active. Replaces the prior 10-sprint v0.9→v1.0 plan in
`handoff_2026-05-06-agentsuitelocal-v090-sprint1-day2.md`.

**Spine:** `/ship` skill (autonomous executor) per sprint.
**Discipline:** layered audit pattern (per-commit careful-coding,
per-checkpoint sanity, per-sprint audit-lite, per-release audit-team).
**Calibration gates:** hard stops between sprints. Three Scott
approvals across the entire 1.0 push.

---

## What changed from the 10-sprint plan

The prior plan committed sprints 1–10 to v1.0. After triage on
2026-05-07, sprints 3, 4, 6, 7, 8 (most of), and 9 were classified
as "robustness / polish / forward-looking" rather than 1.0-blocking.
They slip to 1.1.

**1.0 must include:**
- Test honesty (no lying mocks; MOCKING_AUDIT.md sweep)
- V1/V2 production bug fix (qa_score reliability)
- Bundle integrity smoke (post-PyInstaller first-launch verification)
- Supply-chain hygiene (agentsuite pinned to commit SHA)
- Honest schema (decide `RunRequest.constraints` — wire or remove)
- Bare-min a11y (Tab nav, focus rings, no keyboard traps)
- Final audit-team gate and CHANGELOG/doc-currency sweep

**1.0 explicitly does NOT include** (slip to 1.1):
- Recovery sweeps for Ollama crash / model corruption / disk full /
  key revoke / concurrent runs
- Performance baseline + benchmarks/ harness
- Frozen API surface + schema-change CI
- Full WCAG AA / screen-reader audit / localization
- Landing page polish, code signing, multi-instance, plugin system,
  auto-update, Linux installer, Windows arm64

## Decisions to lock before Sprint A starts

These need answers from Scott before /ship's interactive plan-build.

### D1 — `RunRequest.constraints`: wire or remove?

The field is accepted by the API, stored in no run record, and never
passed to `_AgentRequest`. Two options:
- **Wire it.** Connect `RunRequest.constraints` → `_AgentRequest.constraints`
  → AgentSuite Constraints schema. Adds end-to-end test for the wiring.
- **Remove it.** Drop the field from `RunRequest`. Update API contract
  doc to reflect.

Recommendation: **remove**. If you don't have a constraints feature
shipping in 1.0, the field is dead schema and erodes API trust.

### D2 — A11y bar: how minimum is "minimum-viable"?

Three levels:
- **Bar 1 (recommended for 1.0):** Tab nav works, focus rings visible,
  no keyboard traps, `aria-current="page"` on active nav. ~4-6 hours.
- **Bar 2:** Bar 1 + skip-to-content link + ARIA labels on icon-only
  buttons + alt text on every meaningful image. ~1 day.
- **Bar 3 (slip to 1.1):** Full WCAG AA + screen-reader audit + focus
  management for dynamic content. Multi-day work.

Recommendation: **Bar 1.** Bar 2 is good but the marginal user-impact
of Bar 1 → Bar 2 in a single-user local-LLM desktop app is small.

### D3 — Concurrent runs: documented limitation or in-scope?

Currently the app supports one run at a time per session. The
recovery-sweep watchlist item (W-15 in audit watchlist) covered
making concurrent runs robust. If we slip recovery sweeps to 1.1,
we should document "single sequential run" as v1.0 behavior.

Recommendation: **document the limitation.** Add to README +
user-manual: "v1.0 supports one run at a time per session. Concurrent
runs land in v1.1."

### D4 — Real-e2e branch trigger: keep or remove for 1.0?

`real-e2e.yml` has a push trigger on `release/v0.9.0` that was
added for sprint-time CI convenience. Should be removed at Sprint
B / C. Tracked as ENG-0907-008 in the watchlist.

Recommendation: **remove in Sprint B**, after V1/V2 is confirmed
fixed by 5 consecutive green runs.

## Calibration triggers (auto-replan if hit)

- **Sprint A runs >30% over budget:** stop. Re-scope. Maybe ship
  v0.9.0 from current state and defer 1.0 to a separate milestone.
- **audit-team in Sprint B surfaces a Critical the sprint-A
  audit-lite missed:** stop. Re-plan B with the new finding;
  audit-lite scope was too narrow.
- **Real-e2e fails 3 consecutive runs after V1/V2 fix:** stop.
  V1/V2 fix is incomplete. Diagnose before continuing.

---

## What's NOT in this plan

Per the layered-audit overflow rule, finds at lower altitudes
(per-commit careful-coding) get triaged by severity, not folded in:
- **Blocker** stops the sprint.
- **Critical** only if it fits remaining time.
- **Major** queues to next sprint or 1.1.
- **Minor / Nit** collects in `next-cleanup.md`.

The plan WILL NOT silently expand. If new scope is needed, the
calibration trigger fires and Scott decides.
